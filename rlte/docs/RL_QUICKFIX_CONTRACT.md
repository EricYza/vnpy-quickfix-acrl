# RL 模型与 vn.py / QuickFIX 执行层接口契约

## 1. 适用范围

本契约描述当前固定任务模型 `rlte-strategic-20-v1` 的边界。系统结构建议为：

```text
QuickFIX C++ 引擎
    │ 行情消息、ExecutionReport、会话状态
    ▼
vn.py Python 网关与订单状态机
    │ 构造一致状态快照
    ▼
Python RL 推理模块
    │ 返回目标分配比例（不返回 FIX 报文）
    ▼
vn.py 执行协调器 + 独立风控
    │ reconciliation、报单、撤单、截止清仓
    ▼
QuickFIX C++ 引擎
```

由于前端是 Python，第一版无需跨语言调用模型：vn.py 可以直接调用 PyTorch CPU 推理包装器。QuickFIX C++ 继续负责 FIX 会话和消息传输。只有在完成真实回放并确认部署约束后，才评估 ONNX Runtime 或独立推理服务。

## 2. 调用语义

一次模型调用必须基于同一个逻辑时刻的原子快照：

- 最新完整订单簿；
- 截至该时刻的订单流统计；
- 截至该时刻已确认的自身成交；
- 当前已确认活动订单；
- 所有待确认新单、撤单和改单状态；
- 剩余库存和截止时间。

不得把不同时刻的订单簿、成交和自身订单状态拼成一个观察。模型推理应在行情/订单状态锁之外使用不可变快照，避免阻塞 QuickFIX 回调线程。

## 3. 当前 67 维输入

输入类型是一个长度为 67 的有限 `float32` 向量。完整名称可从 `deployment.schemas.FEATURE_NAMES` 读取。

| 索引 | 数量 | 含义 | 当前仿真计算 |
|---:|---:|---|---|
| 0 | 1 | 归一化时间 | `time / terminal_time` |
| 1 | 1 | 剩余库存比例 | `remaining / initial` |
| 2 | 1 | 最优买价漂移 | `(best_bid - initial_best_bid) / 10` |
| 3 | 1 | 中间价漂移 | `(mid - initial_mid) / 10` |
| 4 | 1 | 归一化价差 | `(best_ask - best_bid) / 10` |
| 5 | 1 | 当前五档盘口不平衡 | `sum(bid_depth-ask_depth)/sum(bid_depth+ask_depth)`；在深度归一化前计算 |
| 6–10 | 5 | 买方五档深度 | 各档原始数量除以训练初始形状中的相应值 |
| 11–15 | 5 | 卖方五档深度 | 同上 |
| 16–20 | 5 | 自身在五个观察价位的订单比例 | 各档活动数量 / 当前剩余库存 |
| 21 | 1 | 五档观察范围外的自身活动订单比例 | 范围外活动数量 / 当前剩余库存 |
| 22 | 1 | 当前未挂出的库存比例 | `(remaining-active) / remaining` |
| 23–42 | 20 | 每手库存的价格层编码 | 见下文 |
| 43–62 | 20 | 每手库存的队列位置编码 | 见下文 |
| 63 | 1 | 最近窗口的市价单不平衡 | `(market_buy-market_sell)/(market_buy+market_sell)` |
| 64 | 1 | 最近窗口的限价单新增不平衡 | `(limit_buy-limit_sell)/(limit_buy+limit_sell)` |
| 65 | 1 | 最近窗口的撤单不平衡 | `(cancel_sell-cancel_buy)/(cancel_sell+cancel_buy)` |
| 66 | 1 | 最近窗口中间价漂移 | `(current_mid-window_start_mid)/10` |

分母为 0 的三个订单流不平衡特征均设为 0。统计窗口是 `[time-time_delta, time]`，当前为最近 15 个仿真时间单位，两个端点都包含。

### 3.1 深度归一化

训练环境不是简单把五档数量除以常数 20，而是加载：

```text
initial_shape/noise_flow_65.npz
```

并使用 `(bidv + askv) / 2` 作为归一化数组。实盘状态构建器若要复现当前模型，必须冻结并版本化这组常数，而不能根据当日行情随意重算。

当前代码在选取归一化切片时使用 `int(normalized_spread - 1)`。这是需要在迁移前复核的历史实现细节，不应在未做一致性测试的情况下“按直觉修正”。

### 3.2 自身订单分布的价位定义

观察构建代码在 `start_at_best_price=True` 时，将五个观察价位定义为：

```text
best_ask, best_ask+1, ..., best_ask+4
```

而动作下单代码把五个限价目标定义为：

```text
best_bid+1, best_bid+2, ..., best_bid+5
```

当价差恰好为 1 时二者一致；价差更宽时二者并不完全相同。这是当前模型训练时真实存在的语义差异。接入真实数据前应决定：

1. 为复现旧模型而严格保留；或
2. 统一定义后重新训练通用模型。

不能在旧模型推理时只改一侧定义。

### 3.3 每手价格层编码

20 个位置分别代表 20 手初始库存。当前未成交库存根据自身活动订单情况编码：

- 位于观察层 `level=1..5`：编码为 `level / 6`；
- 未挂出或在观察范围外：编码为 `6 / 6 = 1`；
- 已成交：编码为 `-5 / 6`。

列表不是稳定的真实 lot ID；它由遍历当前订单簿价位及订单的顺序重建。同类单位在向量中的排列不应被解释成持久身份。

### 3.4 每手队列位置编码

当前最大队列归一化常数为 40：

- 对每个自身订单单位，记录该价位中它前方的单位数量序号，再除以 40；
- 未挂出或在观察范围外：`40/40 = 1`；
- 已成交：`-40/40 = -1`。

代码不会截断超过 40 的实际队列位置，所以该特征可能大于 1。若只有 Market-by-Price 行情，精确复现此特征通常不可行，需要估算或重新设计并训练。

## 4. 当前 7 维输出

输出是目标库存比例：

| 索引 | 字段 | 含义 |
|---:|---|---|
| 0 | `market_sell_fraction` | 当前立即市价卖出的目标比例 |
| 1 | `limit_sell_level_1_fraction` | `best_bid+1` 的目标限价活动库存比例 |
| 2 | `limit_sell_level_2_fraction` | `best_bid+2` 的目标比例 |
| 3 | `limit_sell_level_3_fraction` | `best_bid+3` 的目标比例 |
| 4 | `limit_sell_level_4_fraction` | `best_bid+4` 的目标比例 |
| 5 | `limit_sell_level_5_fraction` | `best_bid+5` 的目标比例 |
| 6 | `inactive_fraction` | 暂时不挂单、不市价成交的目标比例 |

所有值非负且总和为 1。输出是“当前剩余库存的目标分配”，不是新增订单量，也不是原始 FIX 指令。

## 5. 仿真中的比例转整数规则

当前仿真按输出顺序依次计算：

```python
quantity_i = min(round(fraction_i * remaining_inventory), available)
available -= quantity_i
```

最后把所有舍入余数加入 `inactive`。这里使用 NumPy 的 round-to-even 规则。`ExecutionIntent.simulator_target_quantities()` 精确复现该行为。

实盘执行协调器可以先复现该规则用于一致性测试，但长期应明确证券最小交易单位、碎股规则和交易所数量约束。

## 6. Reconciliation：目标分配不能直接发单

vn.py 执行层需要把模型目标与真实订单状态比较：

```text
目标活动数量
  - 已确认活动数量
  - 已发送但尚未确认的新单数量
  + 已发送但尚未确认的撤单数量（谨慎处理）
= 候选调整量
```

必须显式处理：

- 部分成交与撤单同时到达；
- cancel pending 期间原订单再次成交；
- OrderCancelReject；
- NewOrderSingle reject；
- 重复或乱序 ExecutionReport；
- FIX 断线重连后的订单状态恢复；
- 行情变化后价格层映射发生移动；
- 同一母单的累计成交量和 leaves quantity；
- 多策略或人工订单的所有权隔离。

任何时刻都必须满足硬约束：

```text
累计已卖 + 可能成交的活动卖单 + 新发卖单 <= 母单总量
```

模型输出不得绕过该约束。

## 7. 调度与截止时间

当前模型不输出“下次何时调用”。调度器负责调用频率。当前训练对应固定 15 个仿真时间单位一次。

截止逻辑必须独立于模型：

1. 到达 deadline 后禁止再次调用模型创建正常意图；
2. 撤销活动限价单；
3. 处理撤单与成交竞态，得到确认后的真实剩余库存；
4. 按配置的紧急执行策略完成剩余量；
5. 生成完整审计记录。

当前模型不能处理用户任意输入的数量和截止时间。未来通用模型至少应显式输入初始数量、剩余绝对数量、总期限、剩余秒数、决策间隔和紧迫度，并使用固定维度订单特征重新训练。

## 8. 错误处理和降级

模型推理前必须拒绝：

- 非 67 维输入；
- NaN 或 Infinity；
- 超过允许陈旧时间的行情快照；
- 未完成订单簿同步的状态；
- 无法确定真实剩余库存的状态；
- FIX Session 未登录或正在恢复的状态。

模型加载或推理失败时不得继续沿用不明状态，应切换到经过批准的基线执行策略或暂停，由外部风险规则决定。

## 9. 版本和审计日志

每次决策至少记录：

- `contract_version`；
- 模型 SHA-256；
- 母单 ID、symbol、方向；
- 行情时间戳、接收时间戳和决策时间戳；
- 原始 67 维输入；
- 原始 7 维输出；
- 舍入后的目标分配；
- reconciliation 前后的活动订单状态；
- 最终发送、跳过或被风控修改的命令及原因；
- 推理耗时；
- 当前 FIX Session 状态。

日志应允许完全重放一次决策，而不是只记录最终发出的订单。
